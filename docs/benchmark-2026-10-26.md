# 并发压测报告（2026-10-26）

- **环境**：腾讯云 Ubuntu 24.04，4 核 / 3.6G 内存；后端 Spring Boot 2.7（JDK 17）直连 127.0.0.1:9090；MySQL 8.0.46 / Redis 7.0.15 同机
- **工具**：`scripts/bench_reserve.py`（自研 Python 线程池压测脚本，仓库内可复现；JWT 手工签发绕过登录，直测预约接口）
- **前提**：`sudo python3 scripts/bench_reserve.py 20 40`（参数：并发数 / 座位池大小），测试数据跑完自动清理

## 结果

| 场景 | 并发 | 成功 | 失败 | P50 (ms) | P95 (ms) |
| --- | --- | --- | --- | --- | --- |
| A：20 并发抢**同一**座位 | 20 | **1（预期 1）** | 19 | 222 | 222 |
| B：20 并发各抢**不同**座位 | 20 | **20（预期 20）** | 0 | 56 | 74 |

## 解读

1. **场景 A 验证防超卖**：20 个并发请求对同一 AVAILABLE 座位发起预约，条件更新（`UPDATE seat SET status=RESERVED WHERE id=? AND status=AVAILABLE`）保证**恰好 1 个事务更新成功**，其余 19 个因影响行数为 0 收到"手慢了，该座位刚被别人约走"。这是 Spec 2（reservation-integrity-redis）修复 check-then-act 竞态后的回归数据——修复前该场景会产生多条预约记录（超卖）。
2. **场景 B 验证吞吐正常**：无锁竞争时 20/20 成功，P95 74ms（含 BCrypt 验签无关、事务提交 + 内网往返），说明条件更新没有引入正常路径的性能损失。
3. **口径与边界**：这是单机、直连后端、20 并发的小规模验证，用于**功能正确性回归**，不作为容量评估依据；更大的并发（100+）受限于单机 MySQL 与全局 50 QPS 限流（超出部分会被 429 快速失败），多实例容量测试列为后续工作。
