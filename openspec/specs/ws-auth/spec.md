# ws-auth Specification（增量）

## 新增需求

### 需求：WebSocket 握手必须 token 鉴权

连接 URL 仅包含 `roomId` 与 `token`；用户身份、角色、昵称、头像必须由服务端验签 token 后从数据库反查，不信任任何客户端传入的身份字段。

#### 场景：合法用户连接

- **当** 持有效 token 且有有效预约的用户连接某楼层聊天室
- **则** 连接建立，服务端以数据库中的昵称/头像注册会话

#### 场景：无 token 或坏 token

- **当** 连接时不带 token 或 token 验签失败
- **则** 服务端立即以 CloseReason 拒绝，不进入房间校验

#### 场景：伪造管理员被拒

- **当** 普通用户携带自己的 user token、试图以旧式 `role=admin` 参数绕过预约校验
- **则** 系统按 token 中的 role=user 判定，无有效预约即拒绝进入

### 需求：消息身份必须服务端反查

聊天消息广播中的发送者身份（userId、展示名）必须取自服务端会话，客户端消息体中的同名字段被忽略。

#### 场景：伪造他人发言

- **当** 客户端在消息 JSON 中传入他人的 username/userId
- **则** 房间广播与落库记录中的身份仍为该连接的真实身份

### 需求：联动踢人机制在鉴权改造后行为不变（回归）

#### 场景：预约过期踢出

- **当** 在线用户的预约超时或失效
- **则** 60 秒内的定时校验将其断开，CloseReason 说明原因

#### 场景：管理员豁免

- **当** 持 admin role token 的用户连接聊天室
- **则** 不做预约校验，直接放行（沿用既有管理员通道逻辑）
