# reservation-lifecycle Specification（增量）

## 新增需求

### 需求：预约必须到达终态（终态保证）

任何预约最终必须处于 COMPLETED / TIMEOUT / CANCELLED / ADMIN_RELEASED 之一，不允许因用户离线永久停留在 SUCCESS 或 CHECKED_IN。

#### 场景：未签到超时（既有行为保持）

- **当** 预约创建后 30 分钟内未签到
- **则** 60 秒内定时任务将其置为 TIMEOUT 并释放座位（座位从 RESERVED 条件更新回 AVAILABLE）

#### 场景：已签到、预约时段自然结束

- **当** 已签到预约的 end_time 已过（用户未主动退座，例如直接关电脑离开）
- **则** 60 秒内定时任务自动 checkout：置 COMPLETED、记录 real_end_time、释放座位

#### 场景：时段内用户查询当前预约

- **当** 已签到预约仍在 end_time 之内
- **则** getCurrentReservation 正常返回该预约（修复：不再因 timeoutAt 误判为已结束）

### 需求：座位状态变更必须条件化

所有对 seat.status 的更新必须携带预期前置状态（乐观并发），前置不符时放弃更新并记录日志。

#### 场景：定时任务释放已被管理员禁用的座位

- **当** 座位已被置为 MAINTENANCE，定时任务尝试将其从 IN_USE 释放
- **则** 条件更新影响行数为 0，跳过（保持禁用态），记录日志

#### 场景：自动结算后联动踢出聊天室

- **当** 已签到用户的预约被自动结算（COMPLETED）
- **则** 其后一分钟内的聊天室在线校验将其断开（复用既有踢人任务）

# seat-lockdown Specification（增量）

## 新增需求

### 需求：整层禁用必须作废该层活跃预约

管理员将某层座位批量置为 MAINTENANCE 时，系统必须先将该层所有活跃预约（SUCCESS/CHECKED_IN）置为 ADMIN_RELEASED，并尽力通知在线用户。

#### 场景：带占座用户的整层维修

- **当** 3 楼有 10 个活跃预约（含 5 人已签到并在聊天室），管理员禁用整层
- **则** 10 条预约全部变为 ADMIN_RELEASED；座位批量置 MAINTENANCE；5 名在线用户收到 WS 通知（type=reservationCancelled）

#### 场景：恢复启用无逆向动作

- **当** 管理员将整层恢复为 AVAILABLE
- **则** 仅座位状态恢复，不自动重建任何预约

# reservation-concurrency Specification（增量）

## 新增需求

### 需求：并发预约同一座位仅允许一次成功

座位抢占必须以数据库条件更新实现（UPDATE ... WHERE status=AVAILABLE，判断影响行数）。

#### 场景：两人同时抢同一空座

- **当** 两个请求几乎同时预约同一 AVAILABLE 座位
- **则** 恰有一个成功；另一个收到明确失败提示，无重复预约记录落库

#### 场景：抢占后插入预约失败

- **当** 条件抢占成功但后续预约插入抛错
- **则** 事务回滚，座位状态回到 AVAILABLE

# redis-services Specification（新增能力）

## 需求：验证码具备 TTL 与一次性消费

#### 场景：验证码 5 分钟过期

- **当** 验证码生成后 5 分钟内未使用
- **则** Redis key 自动过期，登录校验失败

#### 场景：同一验证码二次使用

- **当** 验证码校验成功完成一次登录
- **则** key 即刻删除，重放同一 key 的登录失败

## 需求：当前用户信息缓存

#### 场景：缓存命中

- **当** 同一用户携带有效 token 短时间内多次访问需要身份的接口
- **则** 第一次后从 Redis 读取用户信息，不查数据库

#### 场景：写路径失效

- **当** 该用户更新资料/改密/被删除/被重置密码
- **则** 缓存即刻删除，下次读取拿到最新数据

#### 场景：Redis 不可用降级

- **当** Redis 连接异常
- **则** 用户信息回退直查数据库（登录主流程不受影响），验证码功能不可用并明确报错
