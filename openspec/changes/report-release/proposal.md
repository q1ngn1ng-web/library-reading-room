# Proposal: report-release（占座举报与限时确认释放机制）【草案，待排期】

> 状态：proposal 已评审方向（用户 2026-10-26 业务讨论提出），未实现。设计定稿前需用户确认细节。

## 为什么

当前"用户签到后离场不退座"只能等到预约时段结束才回收（终态保证兜底），高峰期座位被无谓占用数小时。真实图书馆场景中，**邻座读者是最快的发现者**——需要一个低成本的他律通道，同时保护被举报人免于误伤（限时确认机制）。

## 机制设计（用户原始设想）

```
邻座读者发现座位无人 → 点击该座位"举报占座"
  → 系统校验：该座位确有 CHECKED_IN 预约
  → WS 通知占座人：「您的座位被举报，请在 15 分钟内点击"我还在"确认」
  → 占座人点击确认（任意页面/推送）→ 举报驳回，结束
  → 超时未确认 → 自动结算预约（新终态 REPORT_RELEASED 或复用 TIMEOUT）+ 释放座位 + 通知
防滥用：同一座位被同一人 30 分钟内只能举报一次；确认窗口期内不可重复举报
```

## 改什么（预估）

- 新表 `seat_report`（id, seat_id, reservation_id, reporter_id, deadline, status[待确认/已确认/已释放/已驳回], created_at）
- 后端：POST /reports（举报）、POST /reports/{id}/confirm（确认"我还在"）、定时任务扫超时未确认 → 结算
- 前端：座位图长按/右键"举报占座"；被举报人全局弹窗确认组件；WS 消息类型 `seatReport`
- 复用：WebSocketServer.sendToUser 通道、ReservationServiceImpl.settleReservation 结算、SeatDao.tryUpdateStatus 条件释放

## 非目标

- 不做图片取证、不做举报积分/信用体系（保持本科实现复杂度）
- 管理员强制释放沿用现有整层禁用/单座禁用能力

## 验收要点

1. 被举报人在线：收到 WS 弹窗，点击确认后举报状态=已驳回，座位不变
2. 被举报人离线/不响应：15 分钟后预约结算、座位释放、举报状态=已释放
3. 重复举报在窗口期内被拒绝；deadline 存 Redis TTL 或 DB 均可（设计定稿时选）
